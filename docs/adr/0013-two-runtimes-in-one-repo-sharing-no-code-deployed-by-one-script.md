# Two runtimes in one repo, sharing no code, deployed by one script

Marginly is one repository holding two programs that never meet in source: a
Next.js App Router application on Node, and a set of Supabase Edge Functions on
Deno. Neither imports the other. There is no shared package, no monorepo tooling
and no bundler between them, and everything below follows from that one line.

`CODING_STANDARDS.md` already puts decision logic in Edge Functions and leaves
Next.js as the UI and an RLS-guarded data layer. This decision is what that rule
looks like on disk.

## The boundary, and why nothing crosses it

```
supabase/migrations/        plain SQL, applied by the CLI
supabase/functions/         Deno; the Upload's preview and confirm
src/                        Next.js App Router; the two surfaces of ADR-0011
```

ADR-0009 requires the preview's match and the confirm's match to come from the
same code, and that requirement is satisfied **inside Deno alone** — both halves
of the Upload are Edge Functions, so the matching rules live once under
`supabase/functions/_shared/` and are imported only there. Nothing about that
obligation reaches across the boundary.

What does appear on both sides is ADR-0007's pair: the extraction rules that
produce a Version's text at Upload, and the character-offset to DOM-position
index the reading view builds on every read. That ADR already calls them "one
thing implemented twice, and they are only correct together". This decision does
not fix that and does not try to. A shared package would move the duplication
without removing it — the index has to walk a live DOM and the extractor has to
walk a parsed tree, so they were never going to be one function — and it would
buy that non-fix with a bundler, a dual-target `tsconfig`, and a build step
between the source and both runtimes.

The alternative — one workspace with a `packages/shared` — was rejected on that
trade. It is machinery in exchange for a duplication that survives it.

## App Router

Issue #6 committed to a `/auth/confirm` **route handler** calling `verifyOtp`
server-side, which is a Route Handler and therefore App Router. `@supabase/ssr`
documents its cookie and refresh wiring against App Router middleware, and
ADR-0011 needs exactly two routes, so nothing in the product argues the other
way. The Pages Router would mean rebuilding #6's confirm route as an API route
against an older cookie pattern, for no gain anywhere.

## How the app talks to Postgres

Three clients, one job each, and no secret in any of them:

- a browser client for client components,
- a server client reading cookies from `next/headers`, for Server Components,
- `middleware.ts` running `@supabase/ssr`'s refresh on every request.

That middleware is load-bearing rather than boilerplate. Issue #6 found the
built-in mailer capped at two messages an hour and refusing non-org addresses
outright, so every session it terminates early is spent as a magic-link email out
of a budget that small.

Reads happen in Server Components through the server client. Small mutations —
create, rename and delete a Book, `grant_access`, revoke, and Comment
create/edit/delete — are **Server Actions** calling PostgREST or `rpc`. The
Upload's two halves stay Edge Functions, as ADR-0009 requires.

This does not breach `CODING_STANDARDS.md`'s rule against business logic in
server components. Those mutations are RLS-guarded writes and one `security
definer` function call; the decisions inside them — who may grant, what a
duplicate name is, whether a Book has a Version yet — are in Postgres, where
ADR-0006 and ADR-0010 put them, precisely because PostgREST means the app is not
the only writer.

## Migrations and types

Migrations are plain SQL in `supabase/migrations/`, timestamped by the Supabase
CLI. `supabase db reset` against the local stack is the development and test
database; `supabase db push` applies to the linked project.

Nobody applies them by hand from a terminal history. There is one script, it is
the only path to a deployed change, and a human runs it today — but it is written
so a CI pipeline can call it unchanged rather than reimplement it. That is the
whole reason it is a script and not a runbook.

Schema types are generated by `supabase gen types typescript --local` into
`src/lib/database.types.ts` and **checked in**. `npm run verify` regenerates them
and fails on a diff, so a migration that lands without its types is caught at the
gate rather than at the next person's typecheck. Generating them at build time
was rejected because it makes a clean checkout untypecheckable without a running
database.

## Testing

Two runtimes that share no code cannot share a test runner: running Deno source
under a Node runner needs the bundler this decision exists to avoid. So there are
two, and `npm run verify` runs both.

**Vitest** for the Next.js app — native ESM and TypeScript with no transform
configuration, where Jest needs both. **`deno test`** for the functions, because
it ships with the runtime and adds no dependency to a program whose CPU budget is
already the tightest constraint in the system (issue 15).

`CODING_STANDARDS.md` settles the rest: pure seams get 100% branch coverage, thin
I/O adapters get none, mocks only at the outer edges. The seams this system has
are worth naming, because they are where the hard rules live:

- Deno: the allowlist walk of ADR-0005, the text extraction and segmentation, the
  whitespace normalisation and tie-break matching of ADR-0004, the hash input
  assembly.
- Node: ADR-0012's read-time rewrite of `src`, `srcset` and `<picture>`, the
  offset-to-DOM index, ADR-0007's downward-only collision nudging.

Adapters — the Supabase clients, Storage calls, the raw Postgres connection — are
covered by wiring tests and nothing more.

### The policies are tested against a real database

ADR-0010 warns that a table without a policy is "insecure by omission" and looks
finished. That failure is invisible to every pure-seam test, because there is no
pure seam involved: the rule is in Postgres and it fails open. So the policies get
**TypeScript integration tests in Vitest** against the local stack, driving two
seeded accounts through the promises the product makes — this Reviewer reads this
Book and not that one, a revoked Reviewer loses reading and keeps their address
beside their Comments, Resolve raises for a Reviewer instead of matching zero
rows, an Author cannot grant on a Book with no Versions.

pgTAP under `supabase test db` would assert the same things closer to the
database. It was rejected for adding a third language and a second test command
to state facts the Vitest suite can state in the language the assertions are
already written in.

## Deployment

One script, run in order: `npm run verify`, `supabase db push`, sync the
`edge_functions` role's password, `supabase functions deploy`, `next build`,
restart. The Next.js app is served by `next start` against a production build on
Node — never `next dev`.

The password sync exists because the raw-connection role ADR-0009 needs
(`edge_functions`) is created with no password by its migration — correct, since
`db push` sends that SQL to a linked project verbatim, and a real password can
never live there. An operator sets the matching secret, `EDGE_DB_URL`, by hand
with `supabase secrets set`; that secret is the connection string the Upload Edge
Function actually dials with, so it is the one value that already has to be
right. `scripts/deploy.sh` reads that same `EDGE_DB_URL` from its own environment
and pushes its password into the role, rather than inventing a second value —
one source, read twice, so the two cannot silently drift apart the way issue #40
found them (first deploy after that migration, before this existed).

Vercel was the obvious host and was rejected. It splits deployment across two
mechanisms — a git-driven deploy for the app and a CLI deploy for the functions —
which is exactly the single path this decision is built around, broken in half. A
Node process behind a production build is also container-ready without a rewrite,
so the future CI pipeline is a caller of this script rather than a second
implementation of it.

## `CODING_STANDARDS.md` §5 contradicted the map

The map (issue #1) requires a single imperative subject line with no body and no
trailers, committed directly to `main`, rebasing rather than merging.
`CODING_STANDARDS.md` §5 required Conventional Commits carrying a PR number, with
automated review agents gating a merge. Both cannot hold, and direct-to-`main`
leaves those agents no PR to attach to.

The map wins — it is the standing preference for this repository, where §5's
clause is carried-over boilerplate — and `CODING_STANDARDS.md` is amended to say
so. `npm run verify` is therefore a local gate run before each commit, not a CI
check on a pull request.

## Consequences

**The verify gate is the only gate.** With no pull request there is no second
place a mistake is caught, so `npm run verify` has to be worth trusting: two test
suites, typecheck, lint, and the types-staleness check, all of it fast enough to
run before every commit.

**A migration and its types move together or the gate fails.** That is the
intended cost of checking generated types in, and it means a schema change is
never a one-file commit.

**The extraction/index duplication is now a standing obligation with no
structural help.** ADR-0007 owns the rule; this decision guarantees no shared
module will ever quietly enforce it. Both implementations must be changed
together, and only their tests say so.

**One script is a single point of failure and deliberately so.** A change
deployed any other way is undeployed as far as this decision is concerned, and
the first time someone runs `supabase db push` by hand the script stops being the
truth.

**Local hosting is not production hosting.** `next start` on a laptop satisfies
"not a dev run" and nothing more. Where that process actually lives, and what
restarts it, is not decided here and will be the first thing a real deployment
asks.
